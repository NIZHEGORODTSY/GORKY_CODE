# GORKY_CODE — голосовой ассистент для задач и встреч

Этот файл читают Claude-агенты всех участников команды. Над проектом одновременно работают
несколько людей, у каждого свой Claude. Напрямую агенты общаться не могут, поэтому **единственный
канал связи — этот репозиторий и GitHub** (см. «Протокол координации»). Соблюдай его строго.

Репозиторий: https://github.com/NIZHEGORODTSY/GORKY_CODE (публичный, ветка по умолчанию `main`).

## Что делаем

Тестовое задание: прототип голосового ассистента, который по свободной речи (голосом или текстом)
создаёт задачи/напоминания и встречи, показывает планы на период и ищет старые записи.
Полная сводка требований и критериев оценки — [docs/SPEC.md](docs/SPEC.md). Перед любой работой
над фичей сверься с ней.

Обязательный минимум (4 действия + сохранение данных между запросами):
1. создание задачи / напоминания;
2. создание встречи;
3. список задач и встреч за период («что у меня сегодня / на неделе»);
4. поиск ранее созданной записи по смыслу («найди задачу про договор»).

Главное в оценке — логика: понимание естественной речи, относительные даты, уточняющие вопросы,
чистое разделение слоёв (голос / LLM / бизнес-логика / хранение). UI может быть минимальным.

## Стек и архитектура

Решения приняты 2026-10-30 (менять — только через «Сообщения» в STATUS.md):

- **Интерфейс:** Telegram-бот (aiogram 3, long polling). Текст и голосовые сообщения. Ссылка на
  бота = ссылка на работающий прототип. Telegram `user_id` = пользователь (мультипользовательность).
- **LLM:** GigaChat-3-Pro (Сбер), Python SDK `gigachat`. Сертификат Минцифры — `certs/`, SSL-проверку не отключать. Работа с LLM — только через интерфейс
  `LLMClient` в `app/llm/`, чтобы провайдера можно было заменить (запасной — Claude).
  LLM не пишет в БД сама: выбирает функцию и заполняет аргументы, бизнес-логика валидирует и выполняет.
- **Голос:** распознавание — GigaChat (аудио-вложение, ogg/opus из Telegram как есть; SaluteSpeech для физлиц закрыт с 15.07.2026), озвучка — edge-tts (голос `TTS_VOICE`, при сбое — только текст).
- **Хранение:** PostgreSQL 16, SQLAlchemy 2 (async, asyncpg), миграции Alembic.
- **Поиск:** полнотекстовый Postgres (`russian`); если пусто — GigaChat выбирает подходящие из последних записей (эмбеддинги GigaChat платные).
- **Напоминания:** бот сам присылает сообщение в момент напоминания (фоновая задача).
- **Деплой:** свой VPS, `docker compose` (сервисы `db` и `bot`).

Структура (каждый модуль — зона ответственности, которую можно взять целиком):

```
app/
  bot/        # aiogram: хендлеры текста/голоса, отправка ответов
  assistant/  # оркестрация диалога: история, контекст («перенеси её»), уточняющие вопросы
  llm/        # LLMClient + реализация GigaChat, системный промпт, схемы функций
  speech/     # STT (GigaChat) / TTS (edge-tts)
  core/       # бизнес-логика: доменные модели, разбор дат, валидация, конфликты встреч
  storage/    # SQLAlchemy-таблицы, репозиторий
  search/     # FTS + эмбеддинги, ранжирование
  config.py   # настройки из .env
  main.py     # точка входа
migrations/   # Alembic
tests/
docs/
```

### Контракт данных (менять только через согласование в STATUS.md)

`Event`:
| поле | тип | комментарий |
|---|---|---|
| `id` | int | |
| `user_id` | int | Telegram user id |
| `kind` | `task` \| `reminder` \| `meeting` | |
| `title` | str | содержание задачи / название встречи |
| `starts_at` | datetime \| null | для задачи — срок, для встречи — начало |
| `ends_at` | datetime \| null | только для встреч |
| `all_day` | bool | дата без времени («в пятницу отправить отчёт») |
| `status` | `open` \| `done` \| `cancelled` | |
| `created_at` | datetime | |
| `notified_at` | datetime \| null | когда бот отправил напоминание |

Все даты хранятся с таймзоной (UTC в БД). Таймзона пользователя — в таблице `users` (по умолчанию
`Europe/Moscow`). Текущие дата/время и таймзона всегда передаются в LLM явно вместе с таблицей
ближайших 14 дней с днями недели — модель не должна угадывать «сегодня».

Функции LLM (минимум): `create_event`, `list_events(from, to, kind?)`, `search_events(query,
from?, to?)`, `ask_clarification(question)`. Дополнительно: `update_event`, `delete_event`,
`complete_event`.

## Протокол координации между участниками и их Claude

**В начале каждой сессии**, до любых изменений:
1. `git pull` (или `git fetch` + сверка, если есть локальные изменения).
2. Прочитай [docs/STATUS.md](docs/STATUS.md) — кто чем занят, принятые решения, сообщения тебе.
3. `gh issue list` и `gh pr list` — открытые задачи и PR.

**Задачи** живут в GitHub Issues. Перед началом работы:
- выбери свободный issue (или создай его), назначь своего человека: `gh issue edit <N> --add-assignee @me`;
- впиши строку в таблицу «Кто чем занят» в STATUS.md, закоммить и запушь это **сразу**, чтобы другой
  агент увидел, что задача занята.

**Ветки и PR:**
- в `main` напрямую не пушим; ветка на задачу: `<github-login>/<короткая-тема>`, например
  `petushok08/llm-tools`;
- PR маленькие, в описании — `Closes #N`, что сделано и как проверить;
- чужие модули (занятые в STATUS.md) не правим молча — сначала сообщение (см. ниже);
- перед PR: `git fetch && git rebase origin/main`, тесты проходят.

**Сообщения другому участнику / его Claude:**
- по конкретной задаче — комментарий в её issue или PR;
- общее (вопрос по архитектуре, изменение контракта, блокер) — в STATUS.md, раздел «Сообщения»,
  в формате `- [YYYY-MM-DD] <от кого> → <кому>: текст`. Когда ответили/учли — перенеси в «Решения»
  или удали.
- Подписывай текст от агента: `— Claude (<github-login человека>)`, чтобы было понятно, кто писал.

**В конце сессии:** обнови свою строку в STATUS.md (что сделано, что дальше), запушь ветку.

## Экономия токенов (обязательно)

Лимиты у всех ограничены — расходуй контекст бережно:
- **Отвечай коротко.** Без пересказа сделанного, вступлений и повторения вопроса. Итог — 2–5 строк.
- **Читай точечно.** Сначала `grep`/поиск, потом только нужный диапазон строк (`offset`/`limit`).
  Не перечитывай файл, который уже читал в этой сессии, и не перечитывай после своей правки.
- **Глуши вывод команд:** `-q`, `--quiet`, `| head`, `| tail`, `--oneline`, `pytest -q`. Не выводи
  целиком логи, `pip install`, большие JSON и диффы.
- **Не открывай PDF с ТЗ** — вся нужная информация в docs/SPEC.md.
- **Без субагентов и параллельных сессий**, если человек прямо не попросил.
- **Правки — минимальным диффом** (Edit), а не переписыванием файла целиком.
- **STATUS.md держи коротким:** отвеченные сообщения удаляй, старые строки «Кто чем занят» чисти.
- Не исследуй код «на всякий случай» — только то, что нужно для текущей задачи.
- Если задача неясна — один короткий вопрос человеку вместо долгого перебора вариантов.

## Правила кода

- Код и идентификаторы — на английском; комментарии, документация, сообщения в STATUS — на русском.
- Коммиты: `feat: …`, `fix: …`, `docs: …`, `refactor: …`, `test: …` (текст можно по-русски).
- Секреты (`BOT_TOKEN`, ключи GigaChat/SaluteSpeech и др.) — только в `.env`, который в `.gitignore`. Новые переменные
  окружения добавляй в `.env.example` без значений.
- Бизнес-логику (разбор дат, валидация, поиск) покрываем тестами `pytest`; LLM в тестах мокаем.
- Не плодим зависимости без нужды; новую зависимость — в `requirements.txt` и упоминание в PR.

## Команды

Локально (Windows, Git Bash). Postgres — на VPS, доступ только через SSH-туннель:
```bash
python -m venv .venv && .venv/Scripts/pip install -q -r requirements-dev.txt
cp .env.example .env                       # заполнить; DATABASE_URL с хостом localhost
ssh -N -L 5432:127.0.0.1:5432 <user>@<vps> # туннель к БД, держать открытым
.venv/Scripts/alembic upgrade head          # миграции
.venv/Scripts/python -m app.main            # запуск бота
.venv/Scripts/pytest -q                     # тесты
```
Новая миграция: `.venv/Scripts/alembic revision -m "<что>"` (пишем руками, autogenerate — только как черновик).

VPS: `docker compose up -d --build` (миграции применяются при старте контейнера `bot`).
Один токен бота нельзя одновременно использовать в двух местах (polling) — для локальной
разработки каждому нужен свой тестовый бот от @BotFather.
